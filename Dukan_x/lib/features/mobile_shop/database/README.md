# Mobile Shop Drift Database

Tenant-scoped, version-aware local database for the MobileShop feature. This database is a **non-authoritative** local cache, draft store, mutation queue, and projection. The canonical authority is DynamoDB via `Dukan_x/my-backend`.

## Code Generation

The `.g.dart` file is auto-generated by Drift's `build_runner` integration. It must **never** be manually edited.

### Regenerate command

```bash
dart run build_runner build --delete-conflicting-outputs
```

### When to regenerate

- After modifying table definitions in `mobile_shop_tables.dart`
- After adding new tables to the `@DriftDatabase` annotation in `mobile_shop_database.dart`
- After changing column types, defaults, or constraints
- After bumping `schemaVersion`

### Notes on the `.g.dart` stub

Until `build_runner` is executed, a minimal stub exists at `mobile_shop_database.g.dart`. This stub provides the `_$MobileShopDatabase` base class so that the project compiles without errors during development. Once generated, the stub is fully replaced by Drift's output.

## Migration Workflow

When adding a new schema version, follow this checklist:

### 1. Make the schema change

Edit `mobile_shop_tables.dart` — add columns, tables, or indexes.

### 2. Document the version

In `migrations/mobile_shop_migrations.dart`:

```dart
/// Brief description of what this version adds.
static const int v2DescriptiveName = 2;
```

Update `current` and `supported`:

```dart
static const int current = v2DescriptiveName;
static const List<int> supported = [v1Initial, v2DescriptiveName];
```

### 3. Add migration logic

In `MobileShopMigrationStrategy._applyMigration`:

```dart
case MobileShopMigrationHistory.v2DescriptiveName:
  await m.addColumn(targetTable, targetTable.newColumn);
  break;
```

### 4. Update schemaVersion

The database class reads `MobileShopMigrationHistory.current`, so updating the constant in step 2 is sufficient.

### 5. Regenerate

```bash
dart run build_runner build --delete-conflicting-outputs
```

### 6. Write migration tests

Add tests in the test suite (task 10.4) that verify:
- Fresh install creates all tables correctly
- Upgrade from every supported prior version succeeds
- Queued outbox mutations survive the migration
- Conflict records survive the migration
- Confirmation metadata columns are preserved
- Tenant ownership (tenantId) is never dropped
- Event inbox records are preserved

## Migration Rules (Inviolable)

| Rule | Description |
|------|-------------|
| No outbox drops | Never drop `MobileOutboxMutations` or its columns |
| No conflict drops | Never drop `MobileConflicts` or its columns |
| No confirmation drops | Never drop `confirmationStatus`, `serverVersion`, `syncedAt`, `dataModelVersion` |
| No tenant drops | Never drop `tenantId` from any table |
| No inbox drops | Never drop `MobileEventInbox` or its columns |
| Nullable new columns | New columns must be nullable or have a default value |
| Two-version deprecation | Column removal requires a two-version window |
| Idempotent steps | Migration steps should be safe to re-run when possible |
